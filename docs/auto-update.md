# 自动更新 (一键更新) 的设计与运维

本文写给维护者: 说明"检查更新 → 下载 → 校验 → 替换 → 重启"这条链路的设计、信任边界、
镜像源的维护方式, 以及怎么在不碰真实发布的前提下演练一遍。

## 1. 流程

1. **检查**: 自动检查每天最多一次 (同一版本号只查一次), 手动检查不受限。只有手动检查
   发现新版本后才会继续下面的步骤 —— 自动检查只放一个更新角标, 绝不静默下载。
   无人值守运行 (`--ci-*`、冒烟) 只检查, **不下载、不替换**。
2. **下载**: 逐个尝试配置里的下载源 (见第 3 节), 15 秒连接超时, 失败自动换下一个源。
   成功的源会写进 `update-sources.state` 并在下次提到最前。单个源的响应体上限 512 MB
   (`update_http.c` 的 `UPDATE_DOWNLOAD_LIMIT`), 防的是被换成无限流写满用户磁盘。
3. **校验**: 本地重算 SHA-256, 与期望值逐字节比较。不匹配 → **删除**刚下载的文件、
   保留原程序、报错给用户; 拿不到任何期望值 → 连下载都不做, 直接提示"无法校验, 已取消"。
4. **替换**: 新文件先落在当前 exe 同目录 (`<exe 名>.new.exe`; 目录不可写时退到
   `<cache>/updates/` 并改为提示用户手动替换), 然后主程序正常退出, 由同一个 exe 的隐藏
   模式完成替换:
   `BongoCatTurbo.exe --apply-update --wait-pid=<pid> --wait-mutex=<名> --src=<新文件>
   --dst=<当前 exe> --sha256=<期望值> [--restart-args=<参数>] [--result-file=] [--log-file=]`
   - 运行中的 exe 不能被覆盖, 但**可以被改名** (加载器带 `FILE_SHARE_DELETE`), 于是顺序是:
     旧文件改名 `<exe>.old` → 新文件搬到原名字 → 重新启动。搬新文件失败会把 `.old` 改回去,
     磁盘上始终有一个能跑的程序。
   - "等旧进程退出"用主程序持有的**命名互斥体**实现 (进程死亡时被系统判为 abandoned),
     不使用 `OpenProcess` —— 它在本仓库属于禁用的生产 API
     (`cmake/CheckPlatformRuntimeSafety.cmake`)。
   - 替换前会再校验一次新文件的 SHA-256 (主进程已经校验过, 助手补最后一道闸)。
5. **收尾**: `.old` 保留到新版本**成功启动一次** —— 新版本初始化更新服务时删掉它;
   启动失败则留着可手工回滚。助手替换失败会写 `--result-file`, 下一次启动时读走并提示用户。

## 2. 信任边界 (为什么镜像不可信也没关系)

- 期望哈希只可能来自**官方来源**三处: GitHub API 资源的 `digest` 字段、
  release 说明里的 `SHA256 (<资产名>) = <hex>` 行、同 release 的 `<资产名>.sha256` 资产。
  第三种需要额外抓一次, 但那次抓取**只走官方地址**, 不走任何镜像。
- 镜像 (加速前缀) 只被允许搬运 exe 本体。镜像被投毒/劫持的最坏结果是"校验不通过,
  这次更新取消", 不会装上被篡改的程序。
- 下载地址本身还有前缀校验: 资源名与 URL 最后一段必须完全一致, 且必须落在
  `https://github.com/Fid-falling/bongocat-turbo/releases/download/` 之下
  (`core/update_release.c`)。

## 3. 下载源 (镜像) 的配置与维护

- 默认列表编译在 `src/core/update_source.c` 里: 官方直连 + 若干公共加速前缀。
  **这些公共镜像随时可能失效/限流/换域名**; 失效的表现只是"更新时多等一个连接超时然后
  自动换下一个源", 不影响正确性。维护者直接改那个数组即可。
- 用户/自建镜像可以在**配置目录**放一个 `update-sources.txt` (与 `settings.json` 同级,
  即 `<config 根>/update-sources.txt`; 便携模式下是 `BongoCatData/config/`)。一旦能解析出
  至少一条, 就**完全取代**默认列表。每行一条, `#` 开头是注释, 支持三种写法:

  ```
  direct                                  # 官方直连, 不加前缀
  https://ghproxy.net/                    # 前缀写法: 前缀 + 官方 URL
  https://mirror.example/?u={url}         # 占位写法: 把官方 URL 塞进查询参数
  ```

- `update-sources.state` 是程序自己写的"上次成功的源", 删掉即可恢复默认顺序。

## 4. 安全演练 (不碰真实发布)

`BONGO_CAT_UPDATE_FEED_URL` 环境变量可以把"检查更新"的元数据地址换成本机服务, 用于
演练整条链路 (它不改变信任边界: 期望哈希仍来自那份元数据, 下载后仍要本地重算比对)。

现成的脚本: `pwsh -File scripts/rehearse-update.ps1 -Executable <构建产物>`。它会

1. 把构建产物复制到临时目录并在**副本**上演练 (脚本只用副本, 不碰你正在用的程序);
2. 用同一份副本当"线上新版本"的载荷, 把它的真实 SHA-256 写进假 release 元数据的
   `digest` 字段;
3. 起一个只监听 127.0.0.1 的服务: `/feed` 返回元数据, 其它路径返回载荷;
4. 写好 `update-sources.txt`: 源 1 是连不上的地址 (用来观察"正在尝试第 N/M 个源"),
   源 2 指向本机服务;
5. 打印一条可直接粘贴的启动命令 (带 `BONGO_CAT_UPDATE_FEED_URL` 与 `--storage-root`)。

手工做法也一样: 起一个本地 HTTP 服务提供假 release JSON (版本号更高、资产名与
`BongoCat-<版本>-<平台>-portable.exe` 一致、`digest` 是新文件的真实 SHA-256), 用
`update-sources.txt` 把下载源指到本机, 然后以副本运行:

```
set BONGO_CAT_UPDATE_FEED_URL=http://127.0.0.1:8123/feed
BongoCatTurbo.exe --storage-root=<临时目录副本>
```

点"检查更新"即可看到: 下载进度、当前源、校验、替换、自动重启。想让演练**不替换**任何
东西, 把假 release 的哈希写成错的: 会走到"校验不通过, 已删除下载文件"的拒绝路径。

单元/集成测试已经覆盖同样的链路, 不需要联网:
`ctest -R "update-download|windows-update-self-replace"`。

## 5. 已知边界

- 非 Windows 平台没有"替换正在运行的自己"的通用做法, 手动检查仍然只打开对应的下载页。
- 安装目录不可写 (典型: Program Files 且未提权) 时不尝试替换, 只下载到缓存目录并提示
  "已下载到 `<路径>`, 请手动替换"。
- 替换助手依赖 `ShellExecuteEx`/`CreateProcess` 拉起新进程; 被安全软件拦截时会写失败
  回执并重启旧版本, 用户下次启动会看到提示。
